# 三消/方块消除类 Bot 实战手册（Playbook）

> 本手册沉淀三消类自动化助手的核心架构、踩坑清单与调试方法论，来自一次真实的 Sweet Sugar (Candy Crush 类) bot 构建（胜率 0% → 42%，并推广到 L1-100）。
>
> **何时读**：构建三消 / 网格消除类 bot 时，在步骤2（策略设计）和步骤3（编码）之前读，避免重蹈高频致命坑。

---

## 一、核心架构：加权评分求解器（Weighted-Scoring Solver）

三消 bot 的决策本质极其简单且统一,**不要套用动作类的行为树 / 效用机这类复杂架构**:

```
每个决策周期(棋盘静止时):
  1. 反射读棋盘 → 构建颜色网格快照 (每格: 颜色/类型/是否目标/是否棋盘块/是否原料/特殊糖类型/可移动)
  2. 读所有未完成目标 → 标记网格上的"目标 cell"并按目标剩余量加权
  3. 枚举所有相邻交换(只对"可交换普通棋子"):
       模拟交换 → 检测是否成 3+ 连 → 对匹配线上每个 cell 累加目标加分
  4. 选总分最高的交换 → 通过游戏自身的交换 API 驱动(非模拟鼠标)
  5. 失败回退: 若交换未生效(游戏拒绝/未咬合),加入短期黑名单,下周期选次优
```

**为什么是贪心单步而非多步搜索**:绝大多数三消**回退非法交换**(见 Module C.1),无法跨回合摆布局,所以多步前瞻几乎无收益。贪心单步 + 好的评分函数已能覆盖大部分关卡。

### 评分函数的分层加权(实战验证有效的权重结构)

```
score = 基础消除数(越长越多)
      + 特殊糖造型加分      (L/T +12, 五连 +16, 四连 +6)   // 鼓励造特殊糖
      + 目标色命中 × 权重   (× 12)                          // Destroy 颜色目标
      + 瓶颈目标聚焦        (focusBonus, 按各目标剩余量加权) // 破多目标 1/2 死局
      + 棋盘块目标命中      (× 16, 如 sugar/jelly)           // color=-1 的块目标
      + ReachBottom 序列路由(ingPull, 越近出口越高)          // 原料下落寻路
      + Spread/Block 特殊糖激活(整行/列扫,破吞吐瓶颈)        // 高密度块关卡
      + 定时炸弹邻接拆弹    (+50, 最高优先级)                 // 防爆炸即时失败
```

> 关键设计:**评分用游戏自身的交换做最终验证,所以过乐观的估值无害**——被游戏拒绝的交换会进黑名单跳过。这让评分函数可以大胆加权,不必精确模拟连锁。

## 二、零改动接入(与主 SKILL 一致,三消特化提示)

- 代码隔离按对应引擎手册 §2 的标准姿势(如 Unity 游戏代码全在预定义 `Assembly-CSharp` 时:用**独立可删文件夹 + 命名空间隔离 + 反射**,不要建 asmdef——引用不了预定义程序集)。
- 全程反射读棋盘 / 目标 / 驱动交换,**不改一行游戏代码**。
- **驱动交换走游戏自身的交换方法**(如 `Item.SwitchDirection`),而非模拟鼠标拖拽——确定性高、不受帧率 / 分辨率影响。

## 三、高频致命坑清单(按踩坑代价排序)

> 这些坑的共性:**进程能跑、单看像在动,但结果系统性错误**,极难从启动日志发现。务必逐项排查。

### 🔴 坑 1:坐标系方向搞反(单个影响最大)
- row 增大是向上还是**向下**?很多三消 row 0=顶部、最大 row=底部出口。
- 交换 (col,row)+delta 到游戏方向枚举的映射若错,**垂直 / 水平交换会瞄错邻居**——看似在交换,其实换错位置,匹配永远不成立。
- 本次实战:修正行符号后,某关 25% → 100%。**这是单个最大的稳定性修复。**
- 排查:单步验证"我让 (c,r) 与上方交换,游戏里真的是那两个棋子动了吗"。

### 🔴 坑 2:帧率破坏游戏的匹配 / 交换检测
- 高游戏速度(时间缩放)或不锁帧时,游戏内部的交换 / 下落状态机可能**跳帧失效**,bot 的交换不被识别。
- 本次实战:**锁 60fps** 后才稳定;120fps / 不限帧会破坏检测(Unity 侧为 vSync off + `Application.targetFrameRate=60`,其他引擎用等价的帧率上限设置)。
- 通用:调优 / 验证用 speed=1;高速只用于已稳定通关的关卡做吞吐 sweep。

### 🔴 坑 3:棋盘块目标 ≠ 糖果颜色(机制根因类)
- `color=-1` 的 Destroy/Clear 目标几乎一定是**覆盖在格子上的块**(sugar/jelly),靠"消除其上棋子"清除,**不是匹配某颜色**。
- bot 若按颜色推进,会完全看不到它(本次实战 `focusCells=0`,卡死 L45/50/55 多轮)。
- 正确做法:按**格子 SquareType / sprite** 检测块目标(与 Spread 检测同源),奖励"匹配线经过 / 相邻块格"的交换。

### 🔴 坑 4:碎片棋盘的下落不沿垂直列(ReachBottom 类)
- 原料 / 重力沿格子**预计算的下落序列**(orderInSequence,0=出口)走,碎片棋盘上会拐弯。
- "清同列下方"的启发式在碎片棋盘上找错阻挡格 → 原料卡住(本次实战 L10/15)。
- 正确做法:读每格的 `sequence`,奖励"清除该原料下落序列上、更靠近出口的格"。

### 🟠 坑 5:多目标平均用力 → 1/2 死局
- 多目标关若平均推进,会"完成简单目标、卡死难目标"。
- 正确做法:读各目标**剩余量**,把火力集中到剩余量最大 / 最难的**瓶颈目标**。

### 🟠 坑 6:自动重启 / AI 掩盖胜负检测
- 游戏内置 debug AI / 自动重启可能在 bot 检测到"胜利"之前就重置了棋盘,导致胜利被吞、误判超时。
- 本次实战:进入 Playing 后延迟 2s 关闭游戏内置 AI。

### 🟠 坑 7:多子关卡只跑了第一个
- 多 sublevel 关卡,驱动循环要用 `while(inLevel)` 覆盖全部子关,否则跑完第一个子关就停。

### 🟡 坑 8:教程拦截输入
- 首关 / 特定关教程会吃掉交换输入,bot 须主动清除教程拦截(如调游戏的教程跳过 / 清除方法)。

### 🟡 坑 9:吞吐量上限不是 bug
- 修好机制后仍输的关卡(如 98 个糖霜 ÷ 25 步 ≈ 4/步),是**贪心单步求解器的固有吞吐上限**,不是 bug。
- 破解需特殊糖(条纹一次扫整行/列 ≈9 块/步)或多步攒糖连锁——工程量大、收益集中在少数高难关。**识别这个边界,避免在注定的吞吐瓶颈上空耗迭代。**

## 四、调试方法论(三消特别有效)

### 截图常不可用 → 用代码插桩
- 本次实战中游戏内 `ScreenCapture` 截图**全黑**,无法用于诊断。
- 改用 **verbose 求解器日志**:每周期打印 `网格尺寸 / 目标块数 / 焦点 cell 数 / 各目标剩余量 / 最优分`(如 `block=True(70) maxRem=98 bestScore=74`),配合 battle-log JSON。
- 数值插桩在三消上**比 VLM 更准**——能直接看到"块检测到没有、剩余量在不在降、火力有没有聚焦到瓶颈目标"。

### "机制根因"诊断流程(本手册最核心的方法论)
当某类关卡稳定卡在 X/N 时,按此流程定位:
1. **读目标身份**:插桩打印每个目标的 `action / color / 剩余量 / sprite`。`color=-1` → 立刻怀疑棋盘块目标。
2. **读游戏源码确认清除机制**:这个目标 / 块到底靠什么动作清除一层?(查它的实现类 + DestroyBlock 路径)
3. **对照 bot 评分**:bot 当前有没有奖励这个动作?(看 verbose 里对应的 cell 数是不是 0)
4. **修评分 / 检测,再多次取样验证**。

> 口诀:**真正的根因往往在"游戏机制"而非"我的代码"**。读游戏源码 > 猜。

### 必须多次取样,单次"通关"≠ 修复成功
- 三消是随机游戏。单局 3/3 可能纯属幸运。
- **每关至少 3 次** sweep 才能判断真实效果,否则会把"运气"当"修复",或把"方差"当"回归"。

## 五、方法论可复制性

本次 bot 从 0% 起步,靠同一套循环系统性攻克一类又一类机制:

```
侦察发现高频未解机制(ReachBottom / SugarSquare / Spread / TimeBomb)
  → 读源码定位机制根因(方向 / 载体 / 清除触发)
  → 修反射检测 + 评分规则
  → 多次取样验证
  → 一次修复惠及大量同机制关卡
```

每个机制修复都是"局部改评分函数",不重写架构。这套加权评分求解器 + 机制逐类攻破的范式,可推广到任意三消 / 网格消除游戏。

## 六、与主流程的衔接

- **步骤1 分析**:类型深度层用 `analysis-template-match3-A/B/C-*.md`(实体扫描 / 深挖 / 交互)。
- **步骤2 策略**:核心挑战就是"评分函数设计"。架构**直接选加权评分求解器**(由"回退非法交换"机制自然推导出贪心单步)。
- **步骤3 编码**:决策引擎 = 评分求解器;观察器 = 反射读棋盘网格;输入控制器 = 走游戏交换 API。重点实现本手册第三节的坑 1-8 防护。
- **步骤6 迭代**:三消用**纯 log 诊断法为主**(截图常黑),按"机制根因诊断流程"逐类攻破,每关 3+ 次取样。
