# 三消/方块消除类分析模板 — Module B: 实体深挖

> 适用于：Candy Crush / Sweet Sugar 类、宝石迷阵类、任何"交换相邻棋子凑成 3+ 连消除、按目标完成关卡"的网格消除游戏

## 使用说明

本模板是三消类分析的第 2 个模块（共 3 个）。执行顺序：A → B → C。

**前置依赖**：Module A 的实体 ID 清单。

**认知任务类型**：深度精读。对 Module A 清单中的每个实体精读代码，提取 bot 决策需要的精确属性与触发条件。用 Module A 分配的 ID 索引。

**产出**：实体属性文档。

**评估重点**：准确性——每个块的清除触发条件、每个特殊糖的爆炸范围、每个目标的剩余量读取，是否与代码实现一致？

> **三消深挖的核心目标**：不是把数值抄全，而是回答"**bot 要做什么动作，才能让这个实体朝目标推进一步**"。每个块、每个目标都要落到"一条可编码的评分规则"。

## Module B: 实体深挖

### B.1 棋盘几何与坐标系（必须最先确认）

> 为什么放最前：**坐标系方向搞反是三消 bot 最高频、最致命的 bug**。本次实战中"行号方向反了"曾让垂直交换瞄错邻居、原料下落判断完全相反——是单个影响最大的稳定性问题。

精读棋盘 / 格子 / 交换代码，回答：

| 字段 | 说明 | 为什么 bot 必须知道 |
|------|------|---------|
| 行号方向 | row 增大是向上还是**向下**？（很多三消 row 0=顶部，最大 row=底部） | 决定"下方 / 上方"判断；搞反则下落 / 重力相关全错 |
| 列号方向 | col 增大方向 | 同上 |
| 交换坐标→方向映射 | 交换 (col,row) 与 delta(dCol,dRow) 如何对应到游戏的方向枚举 | **驱动交换的核心**：映射错则永远瞄错邻居，看似在动却换错位置 |
| 棋盘形态 | 是规则矩形，还是**碎片化"岛屿"**（带空洞 / 不规则边界）？ | 碎片棋盘上"重力下落"不沿垂直列，需走游戏的下落序列（见 C） |
| 格子有效性判定 | 哪个字段判定"此格存在且可放棋子"（区分空洞 / 障碍） | 网格构建时跳过无效格 |
| 取格子的入口 | 用什么方法按 (col,row) 取到 Square / Item | 观察器读棋盘的基础 |

**强制结论**：用一句话明确写出本游戏的**行号方向**（"row 增大向下，row 0 是顶部，最大 row 是底部出口"之类），并给代码证据。这一句话直接决定步骤3 的交换驱动与下落逻辑。

### B.2 普通棋子属性

对 Module A 的每个 `item_NNN`：

| 字段 | 说明 |
|------|------|
| ID | 引用 Module A |
| 颜色读取 | 从棋子读颜色 id 的字段 / 属性 |
| 可交换判定 | 完整的"可参与交换匹配"判定条件（如 `Combinable && currentType==NONE && CanGoOut`） |
| 可移动判定 | 该棋子能否被移出当前格（受格子约束 / 障碍限制？） |

### B.3 特殊糖属性

对 Module A 的每个 `special_NNN`：

| 字段 | 说明 |
|------|------|
| ID | 引用 Module A |
| 爆炸方向/范围 | 精确范围：垂直条纹=整列、水平条纹=整行、包装糖=3×3、颜色炸弹=同色全清 |
| 激活入口 | 引爆该特殊糖的具体方法 / 交换方式（bot 主动激活时调用） |
| 生成形状 | 反向记录：什么匹配形状会生成它（供 bot"主动攒特殊糖"） |
| 价值估计 | 一次激活大约清除多少棋子 / 多少目标块（供评分加权） |

### B.4 棋盘块属性（重点）

对 Module A 的每个 `block_NNN`：

| 字段 | 说明 | bot 对应动作 |
|------|------|---------|
| ID | 引用 Module A | — |
| 载体 | 格子属性 vs 独立棋子（再次确认） | 决定检测方式：按格子 type/sprite vs 按棋子 type |
| 检测特征 | bot 在网格里如何识别它（SquareType 枚举名 / sprite 名 / 子格 type） | 网格构建时给 cell 打标记 |
| 清一层的触发 | 精确条件：相邻匹配 / 其上棋子被消 / 落到底部 / 特殊糖波及 | 评分函数奖励能制造该触发的交换 |
| 层数 | 单层还是多层（jelly 常多层） | 影响需要重复触发的次数 |
| 扩散规则 | 是否每回合增殖、增殖速度、如何阻止 | 扩散类需"抢在增殖前清除"，普通 3 连跟不上需用特殊糖 |
| 剩余量读取 | 怎么读"还剩多少块"（常与对应目标的剩余量一致） | 多目标聚焦用 |

> **务必把"清一层的触发条件"写成一句可编码的话**。例如：
> - SugarSquare：「消除坐落在该格上的糖果 → 调 `square.DestroyBlock()` 清一层」→ 评分规则：奖励"匹配线经过 sugar 格"的交换。
> - Spread/Chocolate：「相邻格发生匹配 → 清一层；但每回合自增殖 → 普通匹配跟不上，需特殊糖整行/列扫」。
> - Ingredient（ReachBottom）：「落到底部出口格 → 计数；落点沿格子的下落序列，非垂直列」（详见 C）。

### B.5 目标属性

对 Module A 的每个 `goal_NNN`：

| 字段 | 说明 |
|------|------|
| ID | 引用 Module A |
| 完成判定方法 | 精确方法名（bot 跳过已完成目标） |
| 剩余量读取方法 | 精确方法名 + 参数（如 `GetCount(game:false)`，注意不同参数语义不同） |
| 目标载体 | 该目标是针对"糖果颜色"还是"棋盘块"？（决定 bot 用 color/sprite 焦点 还是 block 焦点） |
| 是否需移出 | 有的目标需棋子真正移出棋盘才算（NotFinishUntilMoveOut） |

> **关键陷阱**：目标的"目标载体"决定 bot 用哪套检测。`color=-1` 的 Destroy/Clear 目标几乎一定是**棋盘块目标**（如 SugarSquare），不能按糖果颜色推进——本次实战正是漏了这点卡死多关。

### B.6 限制属性

对 Module A 的每个 `limit_NNN`：

| 字段 | 说明 |
|------|------|
| ID | 引用 Module A |
| 剩余量读取 | 读当前剩余步数 / 时间的字段 / 方法 |
| 耗尽行为 | 步数 / 时间耗尽时如何判负 |

## 评估重点

本模块的评估重点：**准确性**。

- **B.1 行号 / 列号方向结论是否有代码证据？交换坐标→方向映射是否正确？**（最高优先：搞反则整轮迭代作废）
- B.3 每个特殊糖的爆炸范围是否与代码一致？激活入口方法是否真实存在？
- **B.4 每个块的"清一层触发条件"是否与代码一致、且写成了可编码规则？载体（格子 vs 棋子）判断是否正确？**
- B.5 每个目标的"剩余量读取方法"和"完成判定方法"是否真实存在、参数语义正确？`color=-1` 目标是否识别为棋盘块目标？
- B.6 限制读取入口是否正确？
- 引用的所有类 / 方法 / 字段是否确实存在于游戏代码中？
